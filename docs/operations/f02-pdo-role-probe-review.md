# F02 PDO role probe — review draft

The wrapper is disabled pending independent review. The PHP probe is design material and must not be invoked directly. It uses the existing ignored local administrator password file with the fixed `postgres` login for the dedicated local PostgreSQL instance; the installation record does not identify this administrator or prove that the password authenticates. Neither password nor SQL is passed in arguments, environment or a temporary password file. PHP reads the password in process. The Windows account running the wrapper, its processes, SYSTEM, administrators and the PostgreSQL administrator are trusted. This is not a boundary against another process running as that account; path checks followed by PHP opening paths are subject to same-user replacement races. Do not claim handle-pinned file identity.

The proposed transaction creates a unique NOLOGIN role and explicitly rolls back; it never commits, grants privileges or alters existing roles or databases. Role catalogs are cluster-wide, so an uncommitted role can still cause transient catalog locks and effects until its backend ends. A 45-second client deadline kills the client and reports unknown; this is not proof of server-side termination. Any failure or timeout forbids automated retry and requires an independently verified backend and role investigation. Success requires the original PID and backend start to be absent and the role absent through a fresh, independently guarded connection. No failed-path cleanup is claimed.

The wrapper clears its own completed or partially read byte arrays on a best-effort basis after closing input and waiting for any pending write. Runtime copies, a write that cannot be joined, PDO/libpq internals and crash memory are not proven erased. Timeouts remain unknown outcomes. PHP releases statement references before releasing the primary connection; a synthetic reference-lifetime test models this relationship but does not test a live PDO connection.

The probe only checks transient role flags, absence of memberships, and rollback. It does not check effective CONNECT, schema, relation, sequence, function or default ACL privileges, and makes no access-isolation claim. It does not test a fixture role, tenant RLS or publication. Those remain separate review and implementation requirements.

The revised draft walks `.local` using existing relative directory handles and opens each fixed credential filename relative to the resulting held directory. It checks that each file owner is the current process SID or the SID resolved from the explicitly named local `CodexSandboxOffline` account, with a protected DACL, allowlisted trustees, regular-file status and single-link count; file handles disallow write/delete sharing. Trustees are those two SIDs plus SYSTEM and administrators; no path-derived owner is trusted. Local OS lookup resolved that account, and the current process identity was the repository user. The existing provisioner explicitly allows its process identity, repository owner, SYSTEM and administrators for db-config; it does not itself establish provenance of the separate administrator file. Treat the sandbox account and current user as trusted, subject to security review. The parent can be renamed; retained handles address the opened object, but initial path selection and same-user/admin replacement remain within the trusted boundary. No `.local` ACL was changed. The PowerShell and PHP probe entry points both remain disabled. Credentials are read into bounded frames and sent through stdin; no temporary credential file is created. The fictional frame and handle experiments do not prove real credential authentication, multi-trustee ACL behavior, reparse/hardlink behavior, backend recovery, or successful execution.
